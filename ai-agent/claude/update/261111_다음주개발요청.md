## 1. 프로세스 설계서의 누락 FR 채우기

요구사항 명세서의 FR 중 프로세스 설계서가 다루지 않은 항목은 14개다. 프로세스 설계서 본문에 FR 번호로 연결되는 규칙을 추가해 완성한다.

| FR | 요구사항 | 현재 프로세스 설계 상태 | 채울 내용 (안) |
|----|----------|------------------------|----------------|
| FR-001 | CSV 를 읽어 로컬 DB 에 적재 | P1 에 절차 있음, FR 번호 없음 | P1 표에 FR-001 연결 |
| FR-004 | `word` + `pos` 가 같으면 중복 처리 | 보류 (OI-12) | 품사 확보 후 규칙 작성. 지금은 "보류" 표기 |
| FR-005 | 2,000개 이상 적재, 상한 없음 | 없음 | P1 에 상한 없음과 대량 적재 규칙 추가 |
| FR-011 | 일일 단어는 설정 난이도 범위에서 고른다 | P2 에 있음, FR 번호 없음 | P2 입력 항목과 조건 1~3 에 FR-011 연결 |
| FR-015 | 노출 시각 기록 | 없음 | P2 단계 5 에 `shown_at` 저장 규칙 추가 (구현됨) |
| FR-021 | 재노출 간격 1, 3, 7, 14, 30일 | P3 에 있음 | P3 표에 FR-021 연결 |
| FR-035 | 시험 문제 수는 설정값 (기본 10) | 시험 절차에 있음, 번호 없음 | 시험 출제 절차에 연결 |
| FR-036 | 시험 결과 (날짜, 단어, 뜻, 입력값, 정답 여부) 저장 | 시험 기록 절차에 일부 있음 | 저장 항목 목록 추가 |
| FR-041 | 난이도 설정 (기초, 중급, 심화, 전체) | 설정 반영 절차에 있음 | 설정 항목 표에 연결 (구현됨) |
| FR-042 | 동사 비중 30~90%, 10% 단위 | 설정 반영 절차에 있음 | 설정 항목 표에 연결. 적용은 품사 확보 후 |
| FR-043 | 시험 문제 수 5~20 | 없음 | 설정 항목 표에 추가 |
| FR-044 | 설정 값 기기 저장, 재실행 후 유지 | 없음 | 설정 저장 절차 추가 (구현됨, DataStore) |
| FR-050 | 학습 통계 (2차) | 2차 이관 | 2차 범위 표기만 |
| FR-051 | 오답 목록 (2차) | 2차 이관 | 2차 범위 표기만 |

**완료 기준**
- 위 14개 FR 이 프로세스 설계서 본문에 모두 번호로 연결되어 있다.
- 구현된 항목 (FR-001, 005, 011, 015, 041, 044) 은 "구현 현황" 으로 표시한다.
- 보류 (FR-004, 042 적용) 와 2차 (FR-050, 051) 는 이유와 조건을 함께 적는다.

## 2. 앱이 단독으로 동작하도록 하는 설계 방안

**배경**: 개발이 중단되더라도 이미 설치된 앱은 학습 도구로 계속 쓸 수 있어야 한다. 지금 구조는 서버가 없고 데이터가 기기 안에 있으므로 기반은 갖춰져 있다. 아래는 그 보장을 명시적으로 설계하는 항목이다.

### 2.1 현재 구조의 확인 (이미 충족)

| 항목 | 현재 상태 |
|------|----------|
| 서버, 네트워크 의존 | 없음. 모든 기능이 기기 안에서 동작 |
| 외부 AI, 외부 API | 없음 (ADR-006, ADR-010) |
| 저장 | Room (단어, 일일 목록), DataStore (설정). 기기 밖 전송 없음 |
| 날짜 처리 | 기기 로컬 날짜 기준. 앱을 켤 때 목록을 계산하므로 백그라운드 작업 없이 동작 |
| 설정 복구 | 저장 값이 범위를 벗어나면 기본값으로 읽음 |
| DB 버전 올림 | `MIGRATION_1_2` 로 기존 데이터 보존 (파괴적 마이그레이션 없음) |

### 2.2 보완이 필요한 항목

| 번호 | 항목 | 문제 | 설계 방안 (안) |
|------|------|------|---------------|
| A | 단어 데이터 공급 | 앱에 단어 데이터가 없음 (OI-10 라이선스 미정). 개발이 멈추면 사용자가 CSV 를 직접 준비해야 함 | (a) 라이선스 확인 후 기본 CSV 를 앱에 포함, (b) 포함하지 않고 CSV 가져오기만 유지하며 가져오기 형식 안내를 앱 안에 표시. 둘 중 사용자가 결정 |
| B | 설치본 배포 | 개발이 멈추면 앱 업데이트가 없음 | 설치용 APK 를 확정 버전 (예: v0.x) 으로 태그하고 `docs/` 에 설치 방법 기록. 설치본은 개발 이후에도 실행 가능 |
| C | 앱 업데이트 시 데이터 보존 | 버전이 올라갈 때 데이터가 지워지면 학습 기록이 사라짐 | 모든 DB 변경은 마이그레이션 객체로 작성. `fallbackToDestructiveMigration` 사용 금지. 스키마 파일을 버전마다 보관 (1차에서는 보류했으나 v3 이전에 켬) |
| D | 외부 의존 최소화 | 라이브러리 업데이트가 중단되면 빌드가 깨질 수 있음 | 라이브러리 버전은 `gradle/libs.versions.toml` 에서만 관리 (이미 적용). 설치본 APK 는 그대로 보관하므로 빌드가 깨져도 실행에는 영향 없음 |
| E | 중단 시 최소 기능 정의 | "어디까지 되면 충분한지"가 없음 | 최소 기능 세트: 단어 가져오기, 오늘 목록, 설정 변경, 재실행 후 유지. 시험과 재노출은 있으면 좋은 기능으로 분류 |
| F | 빈 데이터 상태 | 단어가 없으면 목록이 비어 있음 | 빈 상태 안내 (이미 있음). 가져오기 방법을 같은 화면에 표시하는 것으로 보강 |
| G | 인수 점검표 | 설치본이 제대로 동작하는지 확인할 기준이 없음 | 아래 점검표를 테스트 정의서에 포함 |

### 2.3 설치본 점검표 (개발 중단 후 확인용)

1. 앱을 설치하고 처음 실행하면 충돌 없이 빈 상태 화면이 뜬다.
2. CSV 를 가져오면 저장 개수가 맞게 표시된다.
3. 앱을 완전히 종료한 뒤 다시 켜도 단어가 남아 있다.
4. 오늘 목록이 만들어지고, 같은 날 다시 켜도 같은 목록이 나온다.
5. 설정 (개수, 난이도) 을 바꾸면 저장되고, 다시 켜도 값이 유지된다.
6. 기능어가 목록에 없고, 오른쪽 TIP 칸에 표시된다.
7. 휴대폰을 비행기 모드로 두어도 위 1~6 이 모두 동작한다.

### 2.4 결정이 필요한 것

1. A 항목: 단어 데이터를 앱에 포함할지 (라이선스 확인 필요)
2. E 항목: 최소 기능 세트에 재노출과 시험을 포함할지
3. B 항목: 설치본 배포 방식 (APK 직접 설치 또는 다른 방법)

## 3. 작업 순서 (안)

1. 결정 사항 (2.4) 확인
2. 프로세스 설계서 누락 FR 14개 채우기 (1절)
3. 설치본 점검표를 테스트 정의서에 반영 (2.3)
4. 아키텍처 결정 기록에 "앱 독립 동작" 결정 추가 (제안 상태로 기록)
5. 기기에서 점검표 1~7 실행
